# S5 — Pipeline Integration — Design

**Status:** Brainstormed 2026-05-21. Implementation plan: pending.
**Surfaces:** `backend/` only — pipeline service + AI phase builders + connector viewmodel + a new ARQ worker task. No frontend changes.
**Slice:** S5 of the M16-M20 roadmap (S1-S4 complete).

---

## Goal

S1-S4 built up "client context" — structured `Client.context_profile` data, plus connector-synced emails/docs/meetings/Slack mentions. The proposal pipeline mostly **ignores** it: of 7 phases, only `run_research` consumes `context_brief`. S5 makes the pipeline actually *use* the client intelligence S1-S4 collected, and closes the loop so synced emails feed back into the context profile.

Three pieces:
- **A — Context-brief wiring:** thread `context_brief` into the 4 phases that ignore it, and fix the regeneration problem (it's currently regenerated by an LLM call every time it's needed).
- **B — Cost model preferences:** make `build_cost_model` consume `proposal.preferences`.
- **C — Post-sync email auto-enrichment:** synced emails (`email_index` table) currently dead-end; feed them into `Client.context_profile` via a background job.

## Non-goals

- Persisting `context_brief` on the `Client` for cross-proposal reuse — chose a per-proposal snapshot instead (see Piece A rationale).
- Backfilling `email_index` rows synced before this ships into context profiles.
- New pricing math in `CostModelBuilder` beyond honoring the `pricing_model` / `discount_tags` preference keys.
- Changing `run_research`'s existing (working) `context_brief` wiring.
- Frontend changes — S5 is entirely backend.
- Fixing the unrelated dead paths the exploration flagged (`ResearchAgent.research_client`, hardcoded 18% GST) — out of scope, noted for a future cleanup.

## Current state (from codebase exploration)

- **Pipeline phases** run as independent ARQ jobs (`backend/app/workers/pipeline.py`), each with its own DB session. `pipeline_service.py` has one method per phase. Auto-chaining via `_NEXT_PHASE` map; human-approval gates enqueue research/narrative/outputs.
- **`context_brief`** is produced by `ContextService.generate_context_brief(client_name, context_profile)` (`context_service.py:117`) — an LLM call. **Not persisted.** `PipelineService._load_context_brief(proposal)` (`pipeline_service.py:77`) regenerates it on every call. Only `run_research` calls it today (`pipeline_service.py:172`).
- **`Proposal.preferences`** exists (`proposal.py:33`, `JSONColumn`, default `{}`). Read only by `_merge_preferences_into_config` (`pipeline_service.py:641`), which is called only in `generate_narrative`. `build_cost_model` never sees preferences.
- **`CostModelBuilder.build`** (`cost_model_builder.py`) takes `template_config` only — multipliers from `template_config.cost_model.default_multipliers` + hardcoded brief-signal heuristics.
- **Email sync** (`sync_emails`, `connector_viewmodel.py:208`) writes classified rows to the `email_index` table. Nothing reads `email_index` into context. `ContextService.enrich_context_with_emails` (`context_service.py:193`) exists, takes the exact email-summary shape `EmailIndex` rows carry, but is never called. (Drive/Calendar/Slack syncs DO write to `context_profile`; email is the gap.)

## Piece A — Context-brief wiring

### A.1 Persistence (foundation)

Pipeline phases are separate ARQ jobs — a brief generated in one phase cannot be held in memory for the next. It must be persisted between phases.

**Add a nullable `context_brief` TEXT column to the `Proposal` model.** This matches the existing pattern: `research` and `benchmarks` are already `Text` columns on `Proposal` holding per-run phase artifacts. One alembic migration.

**Rationale for Proposal-level (not Client-level):** a pipeline run is a point-in-time artifact; its research/benchmarks/cost_model are all snapshots stored on the `Proposal` row. `context_brief` is the same kind of thing — the client context as-of when this proposal was built. Client-level storage would optimize for "same client, many proposals" reuse but requires cache-invalidation logic (hash the `context_profile`, compare on read). Proposal-level needs none.

### A.2 `_load_context_brief` becomes get-or-generate-and-persist

Rework `PipelineService._load_context_brief(proposal)`:

```
if proposal.context_brief is not None:
    return proposal.context_brief
brief = <generate via ContextService — existing logic>
if brief:
    proposal.context_brief = brief
    <persist: update the proposal row>
return brief
```

The first phase to call it pays the one LLM call + one DB write. Every later phase — same run, or a retry — reads the column free. Self-healing: no dependency on a specific phase running first. Stays **best-effort** — if generation fails (no client, LLM error), it returns `None` and phases proceed without a brief, exactly as today. Generation must not block a proposal.

Persistence detail: each phase has its own session and loads its own `proposal` row. `_load_context_brief` writes `proposal.context_brief` and **commits it immediately** (its own commit, not deferred to the calling phase's later commit) — so the brief is durable even if the calling phase subsequently fails. A later phase reloads the proposal and sees the persisted value; a retry of the failed phase reads it free.

### A.3 Wire the brief into 4 phases

`run_research` already consumes it (`pipeline_service.py:172`) — unchanged. Add it to:

| Phase | Builder / prompt | Injection |
|---|---|---|
| `analyze_brief` | `BriefAnalyzer.analyze` (`brief_analyzer.py`) | add a `context_brief: str \| None` parameter; when present, render a `## Existing client context` block into the analyzer's system prompt |
| `run_benchmarks` | `BENCHMARK_SYSTEM` prompt + user message (`pipeline_service.py` ~:279) | add a context block to the benchmark prompt the same way `run_research` does |
| `generate_narrative` | `NarrativeGenerator.generate_all` (`narrative_generator.py`) | add a `context_brief: str \| None` parameter; thread into the covering-letter and scope-section prompts |
| `run_ideation` | `IdeationService._build_ideation_system_prompt` (`ideation_service.py:77`) | add a `## Client context` block to the ideation system prompt |

Each phase obtains the brief by calling `_load_context_brief(proposal)` (now self-healing). For `run_ideation`, which lives in `IdeationService` not `PipelineService`, the brief is loaded the same way — `IdeationService` already instantiates a `ProposalRepository`; it loads the proposal and reads `proposal.context_brief`, generating-and-persisting via `ContextService` if the column is null (same get-or-generate logic — extract it into a shared helper so `PipelineService` and `IdeationService` share one implementation).

**Shared helper:** to avoid duplicating the get-or-generate-and-persist logic across `PipelineService` and `IdeationService`, put it on `ContextService` (or a small standalone function) — e.g. `ContextService.get_or_create_proposal_brief(proposal, client, proposal_repo)`. `_load_context_brief` becomes a thin wrapper. One implementation, two callers.

When the brief is `None` (no client, generation failed), every phase's prompt simply omits the context block — no error, no empty heading.

## Piece B — Cost model consumes `proposal.preferences`

`build_cost_model` (`pipeline_service.py` ~:344) currently calls `CostModelBuilder.build` with `template_config` only.

**Change:** `build_cost_model` calls the existing `_merge_preferences_into_config(template_config, proposal.preferences)` helper (the same one `generate_narrative` uses) and passes the **merged** config into `CostModelBuilder.build`.

`CostModelBuilder.build` is updated to read two keys from the merged config:
- **`pricing_model`** — selects the pricing approach where the builder currently hardcodes one (e.g. fixed-fee vs time-based line items). If absent, the builder behaves exactly as today.
- **`discount_tags`** — a list of tags applied as additional cost multipliers, layered on top of the existing brief-signal heuristics (rush / annual / existing-client). Each recognized tag maps to a multiplier from `template_config.cost_model.default_multipliers` (the same source the existing heuristics use). Unrecognized tags are ignored (logged at debug).

**Empty-preferences behavior:** `proposal.preferences == {}` → `_merge_preferences_into_config` is a no-op overlay → `CostModelBuilder.build` produces byte-identical output to today. This is the regression guarantee.

Scope boundary: S5 plumbs the merged config through and has `CostModelBuilder` honor those two keys using the multiplier source it already uses. It does **not** invent new pricing formulas.

## Piece C — Post-sync email auto-enrichment

### C.1 New ARQ worker task

Add `enrich_context_from_emails` to the worker (`backend/app/workers/`), registered in `WorkerSettings` alongside the existing pipeline phases.

**Signature:** `enrich_context_from_emails(ctx, agency_id: str, client_ids: list[str])` — the agency plus the specific clients that received new emails in the triggering sync.

**Behavior:** for each client id:
1. Load the client; load its `EmailIndex` rows (filtered to that client's `client_domain` / `client_name`).
2. Build the `email_summaries` list in the shape `ContextService.enrich_context_with_emails` expects (`subject` / `summary` / `sentiment` / `message_type` / `date` — exactly what `EmailIndex` rows carry).
3. Call `ContextService.enrich_context_with_emails(client_name, current_profile, email_summaries)` → merged profile.
4. Write the merged profile back via `client_repo.update`, tagging the email source (mirroring how Drive/Calendar/Slack syncs tag `_sources`).

**Terminal, like pipeline phases:** a failure writes a structured log event (`event: connector.enrich.failed`) and returns cleanly — it does NOT retry and does NOT fail the sync that enqueued it. Per-client errors are caught individually so one bad client doesn't abort the rest.

### C.2 `sync_emails` enqueues the job

In `ConnectorViewModel.sync_emails`, after the email rows are committed and the per-domain watermarks updated, collect the set of clients that received **≥1 new email** this run (the per-domain watermark logic already distinguishes new vs not). If that set is non-empty, enqueue one `enrich_context_from_emails` job for the agency with that client-id list.

- **Idempotency key:** `{agency_id}:enrich_context:{timestamp}` — each sync that produced new emails enqueues a fresh job (not deduplicated; every sync with new signal should enrich).
- Clients with zero new emails this run are not in the list — no wasted LLM merge.
- If the whole sync produced zero new emails, no job is enqueued.
- Enqueue failure (Redis down) is logged but does not fail `sync_emails` — the sync itself succeeded.

## Data flow summary

```
analyze_brief ──┐
run_research    ├─ each calls _load_context_brief(proposal)
run_benchmarks  ├─ → first caller generates + persists Proposal.context_brief
generate_narrative ┘   → rest read the column (no LLM call)
run_ideation ─── loads proposal, same get-or-generate-and-persist via shared helper

build_cost_model → _merge_preferences_into_config(template_config, proposal.preferences)
                 → CostModelBuilder.build(merged_config)   # honors pricing_model + discount_tags

sync_emails (commit + watermarks)
   → clients with ≥1 new email → enqueue enrich_context_from_emails(agency_id, client_ids)
        → per client: EmailIndex rows → ContextService.enrich_context_with_emails
        → merged profile → client_repo.update (tagged with email source)
```

## Error handling

| Failure | Behavior |
|---|---|
| `context_brief` generation fails | `_load_context_brief` returns `None`; phases omit the context block; proposal proceeds |
| `proposal.preferences == {}` | merge is a no-op; cost model output identical to pre-S5 |
| unrecognized `discount_tags` entry | ignored, logged at debug |
| `enrich_context_from_emails` job fails | structured log event, no retry, sync unaffected |
| per-client error inside the enrich job | caught per-client; other clients still processed |
| enqueue fails (Redis down) | logged; `sync_emails` still returns success |

## Testing

**Piece A**
- `_load_context_brief` / shared helper: first call generates + persists `Proposal.context_brief`; second call reads the column and makes no second LLM call (assert via a generation spy).
- Each of `analyze_brief`, `run_benchmarks`, `generate_narrative`, `run_ideation`: assert `context_brief` reaches the builder/prompt call (mock the service method, inspect the args / rendered prompt). Assert the context block is omitted when the brief is `None`.
- Migration: the new column is nullable; existing proposals load fine with `context_brief = NULL`.

**Piece B**
- `build_cost_model` passes a merged config carrying a `discount_tags` preference into `CostModelBuilder.build` (assert via arg inspection).
- `discount_tags` apply as multipliers; `pricing_model` selects the approach.
- Regression: `preferences == {}` → cost model output identical to a pre-S5 baseline fixture.

**Piece C**
- `enrich_context_from_emails` task: stub `ContextService.enrich_context_with_emails`; assert only the passed `client_ids` are processed, `context_profile` is updated, email source tagged.
- per-client error isolation: one client raises, the rest still complete.
- `sync_emails`: after commit, asserts an `enrich_context_from_emails` job is enqueued with exactly the clients that got new emails; asserts NO job enqueued when zero new emails.

**Test infrastructure** (from exploration): pipeline phases tested by patching the service method (`monkeypatch.setattr(BriefAnalyzer, "analyze", fake)`); ARQ tasks tested in `test_pipeline_worker.py`; `conftest.py` autouse `_no_network` blocks real LLM calls; `make_proposal_db` seeds proposals; `arq_pool` is a mock pool; `ws_publish_spy` captures broadcasts.

## Acceptance criteria

- [ ] `Proposal` has a nullable `context_brief` TEXT column; migration applies cleanly
- [ ] `_load_context_brief` generates+persists on first call, reads the column thereafter — verified by a no-second-LLM-call test
- [ ] `analyze_brief`, `run_benchmarks`, `generate_narrative`, `run_ideation` each inject `context_brief` into their prompt when present, omit it when `None`
- [ ] `build_cost_model` passes a preference-merged config into `CostModelBuilder.build`
- [ ] `CostModelBuilder` honors `pricing_model` and `discount_tags`; empty preferences → identical output
- [ ] `enrich_context_from_emails` ARQ task exists, processes only changed clients, updates `context_profile`, is terminal on failure
- [ ] `sync_emails` enqueues the enrichment job after commit for clients with new emails, and skips enqueue when there are none
- [ ] `pytest` green; no regressions in the existing pipeline / connector test suites
